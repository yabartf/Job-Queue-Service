# AI Tool Usage

## Tools I Used

**Claude Code (Opus)** — the primary tool, used for the whole cycle: drafting specifications, implementing against them, and generating the test suite.

## How I Worked

Spec first, code second. For every part of the system I wrote a specification in `specs/`, reviewed it, and only then implemented against it:

1. `specs/00-architecture.md` — components, data flow, invariants, and the alternatives I rejected
2. `specs/01-data-model.md` — schema, constraints, indexes, state machine
3. `specs/02-api-core.md` — HTTP contract, job class hierarchy, validation and security model
4. `specs/TEST_PLAN.md` — a numbered scenario matrix across three test levels

The specs are not documentation written after the fact. They are what the code was written against, and the test IDs in the plan (`L1-23`, `L2-14`, `E2E-12`) appear as the actual test names in the suite, so any claim in a spec can be traced to the test that holds it. Where implementation taught me something the spec had wrong — see the SSRF case below — I changed the spec in the same commit rather than letting the two drift.

The decisions that came out of this process are in `DECISIONS.md`, each written when it was made rather than reconstructed afterwards.

## What Helped Most

**Exhaustive test matrices.** This is where AI earned its place. The suite contains a case per CHECK constraint, a 4×9 payload-validation matrix across every job type, and about thirty SSRF inputs covering loopback, private ranges, link-local, IPv4-mapped IPv6, blocked suffixes and malformed URLs. Writing that breadth by hand is exactly the work where attention fades and you stop at the three obvious cases. It paid off concretely: the constraint matrix passed on the first run and confirmed the schema, while the SSRF matrix found **two real holes** in code I had already convinced myself was complete.

**Structured comparison of queue technologies.** Before committing to an architecture I worked through Redis lists with `BRPOP`, sorted sets with `BZPOPMIN`, Redis Streams with consumer groups, and RabbitMQ priority queues. Getting each option's mechanics laid out — including the detail that Redis gives you at most two of {priority, reliability, blocking}, and that RabbitMQ's priority stops applying once messages are prefetched — turned a day of reading into an hour. The *choice* was still mine; what AI supplied was the map, not the destination.

## What I Had to Fix

**A concurrency test that would have proven nothing.** The idempotency-under-concurrency test is one of the six the assignment requires. The natural way to write it is to reuse the shared database fixture the rest of the suite uses — a session inside a transaction that is rolled back on teardown. That is wrong, and quietly so: ten "concurrent" submissions on one connection inside one transaction are executed in sequence. The test goes green while asserting nothing whatsoever about concurrency. It needed a separate fixture (`committing_sessions`) with genuinely independent connections, real commits, and truncation cleanup. A test that passes and is vacuous is worse than no test, because it also removes the pressure to write a real one — this is the failure I would most expect an AI-written suite to contain, and the reason I now read concurrency tests for what they actually execute rather than what they claim to cover.

**The same failure again, two parts later — and this time I was looking for it.** Every concurrency test in the suite ran against `NullDispatch`, so the Redis path, which is what actually runs in production, was the one never put under concurrent load. The obvious test is to seed a backlog, start a worker wired to a real Redis, and assert nothing ran twice. It passes. It also passes with no Redis at all, because a slot consults the dispatch only when its own scan came back empty, so a pre-seeded backlog is drained entirely through the fallback with Redis merely attached. I caught it by reading the log output of my own passing test and noticing `from_hint=False` on all forty claims. The fix has two parts: the worker has to be running and idle *before* the work arrives, and the assertion has to be the `from_hint` flag the claim records in `job_logs` rather than "the queue still drained". I then swapped the dispatch back to `NullDispatch` to confirm the test fails — which is the step that turns a belief into a check. The lesson from the wiring bug below was already written down; it took a second occurrence for me to apply it before rather than after.

**`ON CONFLICT DO NOTHING` against a partial unique index.** Duplicate prevention rests on a unique index that is partial (`WHERE idempotency_key IS NOT NULL`), so that the many jobs submitted without a key do not all collide on `NULL`. The first version of the insert inferred the conflict target from the column alone. PostgreSQL cannot resolve a partial index without also being given its predicate, so this fails at runtime — and only on requests that carry an idempotency key. The fix is one argument (`index_where`), but the shape of the bug is instructive: correct-looking code, failing on a path the happy case never touches.

**The ownership predicate on the completion write.** The obvious way to finish a job is `UPDATE jobs SET status='completed', result=... WHERE id=$1`. That is a data-loss bug. If the worker stalled long enough for its lease to expire, the reaper has already returned the job and another worker may have completed it; the stalled worker then wakes up and overwrites a legitimate result with its own stale one. The write has to be conditioned on still owning the job — `AND worker_id=$me AND status='processing'` — and the worker must discard its own result when that matches zero rows. Nothing about the happy path suggests this is necessary, and no test of a single worker will ever surface it. It is documented in `DECISIONS.md` §2 because it is the single most important line in the whole design.

**Two clocks deciding one comparison.** The retry deadline was computed as `clock.now() + delay` in Python and stored; the claim query decides whether a job is due with `scheduled_at <= now()` evaluated by PostgreSQL. Those are different clocks, and every retry would have fired early or late by exactly the skew between the worker host and the database — silently, since nothing compares them. It surfaced only because the integration tests run against a frozen clock, which is a very large skew, and a job scheduled two hours in the past became instantly claimable. A few hundred milliseconds of real skew would have produced the same defect with none of the visibility. Deadlines are now computed in SQL as `now() + interval`; the injected clock survives only for values the database never compares.

**A worker that ran every job and was still wired wrong.** The worker's entry point built its dependency graph with `NullDispatch` — the no-Redis fallback — instead of the real client. Every test passed. Jobs were submitted, claimed, executed and completed; the suite was green at 100 % coverage. The bug is invisible to tests *by design*: the fallback claim against PostgreSQL is what guarantees correctness, so a worker with no dispatch behaves identically, only slower. What exposed it was running `docker compose up` and reading the health endpoint, which reported `workers: {count: 0}` while jobs were visibly completing, and a `ready_hints` count that climbed and never fell. The lesson I took from it is narrow and useful: a component whose failure mode is *graceful degradation* cannot be verified by asserting that the system still works, because that is exactly what it does when it is broken. It needs a test that asserts the wiring itself, which the suite now has.

**A load test that measured the test harness.** The concurrency load test took twenty minutes and timed out. Nothing was wrong with the queue: the fixture built its sessions on SQLAlchemy's `NullPool`, so every one of the thousands of short units of work a worker opens meant a fresh TCP connection and a fresh authentication. Switching the fixture to a real pool — which is also what production uses — brought the same test to 3.5 seconds. A slow test is easy to misread as a slow system, and I would have gone looking in the wrong place.

**A guard written for one path and forgotten on the identical one.** The reaper has two statements because a job whose lease expires with no attempts left cannot go back to the queue — the next claim would compute `attempts + 1` past `max_attempts` and violate a CHECK constraint. That is documented in the spec, in the code, and in a test. The graceful-shutdown release does the same thing to the same column and had one statement. A deploy landing on a job's final attempt would return it to `pending` with its attempts spent, and because the claim selects by priority and age, that single row would then be picked first by every worker in the fleet and raise an `IntegrityError` every time — with the reaper unable to clear it, since the job is `pending` rather than `processing`. I found it by reading the two code paths next to each other rather than by testing either. What makes it worth recording is that the constraint had already taught this lesson once, in writing, twenty lines away.

**A warning that means "Redis is down" firing every five seconds against a healthy Redis.** `next_hint` blocks on `BZPOPMIN` for the poll interval, which is 5 seconds; redis-py's default socket read timeout is also 5 seconds. The socket always wins, so every idle poll raised instead of returning empty, and each raise logged `dispatch.next_hint_failed` — the same line that means the server is unreachable. Nothing broke: the dispatch degrades to "no hint" and the PostgreSQL fallback carries the work, which is precisely why the suite and the Docker smoke test stayed green. I only caught it by reading `docker logs` on a stack I believed was healthy. Two library defaults that happened to be equal, neither of them visible in the code.

**Cancelling a coroutine does not cancel the tasks it started.** `Worker.run` created its slot and maintenance tasks and then awaited a stop event. Cancelling `run` left every child running — a worker that had been told to die, still claiming jobs nobody was supervising. This only surfaced because the load test simulates a crash by cancelling the worker and then asserts that the jobs it was holding get recovered; they were not stranded, because the "killed" worker cheerfully finished them. The fix is a `finally` that cancels the children, and the shape of the bug is worth remembering: structured concurrency is not the default, and `asyncio.create_task` hands you an object whose lifetime you are now responsible for.

## What AI Struggled With

**Library behaviour it assumed rather than verified.** Pydantic v2 returns IPv6 hosts bracketed — `url.host` for `http://[::1]/x` is the string `"[::1]"`, which `ipaddress.ip_address()` refuses, so the address fell through to the "it must be a hostname" branch and was accepted. Loopback over IPv6 sailed straight past an SSRF check that looked airtight. The same test matrix showed that pydantic normalises `https:///path` into the host `path` — which led to a rule that was in no spec I had written: **reject single-label hostnames**, because `http://intranet` resolves through the local search domain to an internal host. Two of the security control's real defences came from testing its assumptions, not from designing it. (Starlette had also renamed its 422 and 413 status constants; less interesting, same root cause.)

**Tooling interactions that produce a plausible wrong number.** Coverage reported 96 %, with the line after every `await session.execute(...)` marked unreached. That is a believable result, and the obvious reaction is to go write tests for the "uncovered" code. The real cause is that SQLAlchemy's asyncio layer runs its synchronous core inside greenlets, and coverage loses the tracer across the switch; the fix is `concurrency = ["thread", "greenlet"]` in one config file. The lesson is not about coverage — it is that a tool reporting a specific, plausible number is more dangerous than one that fails outright, because nothing prompts you to question it.

**Noticing that a knob nothing turns.** `BaseJob.timeout_seconds` was written into the job hierarchy in part 1 — 60 by default, 120 for reports, 300 for batches — and until part 3 **nothing read it**. It survived two parts of the project and a suite at 100 % coverage, because nothing fails when a setting is merely ignored: there is no error, no uncovered line, no failing assertion. I found it by re-reading the requirement list rather than the code. Dead configuration is the one kind of dead code that tooling cannot see, and the only defence is periodically asking what each knob is *for*.

**Noticing that a name was already taken.** `JobRepository` had a method called `list`. Adding a later method annotated `-> list[UUID]` made the module fail to import: inside a class body the name `list` now refers to the method, not the builtin, and annotations are evaluated as the class is defined. The suggested fix was `from __future__ import annotations`, which makes the error disappear while leaving the shadowing in place for the next person. I renamed the method instead. This is a recurring shape — the offered fix silences the symptom, and deciding whether that is the right trade is not something the tool is positioned to judge.

**Deciding anything that depends on context it cannot see.** Every "which of these two correct designs belongs here" question came back as a balanced summary of both. Making Postgres the source of truth and demoting Redis to a dispatch hint; bounding `priority` to 0–9 so a client cannot submit `2^31-1` and pre-empt the queue permanently; dropping `total` from list responses so the endpoint an operator refreshes most does not run a full count each time; answering an idempotent replay with 200 rather than 201 so a client retrying after a timeout can tell whether its first request landed — none of those were suggested to me. They are judgements about this system's constraints, and AI is a good instrument for laying out the options and a poor one for choosing between them.

## On Reviewing the Output

The working rule was that anything I could not explain does not ship. In practice that meant keeping the code small and refusing speculative abstraction: no configuration knobs nothing reads, no defensive branches guarding conditions that cannot occur, no layers added "for later". `ruff`, `ruff format` and `mypy --strict` all run clean, but those catch style and types — they say nothing about whether a design is right. The parts that needed real scrutiny were the ones above: the concurrency test, the conflict-target inference, and the ownership predicate. All three looked correct and were not.

The last pass was a review of the finished repository, run against a live stack rather than only against the source. It produced eleven findings, three of them worth stopping for — the shutdown release, the slot loop, and the Redis read timeout above. It also produced three that did not survive checking: an IPv4-shorthand SSRF bypass (pydantic normalises `http://127.1` to `127.0.0.1` before the validator sees it), a rollback failure in the health endpoint's database-down path, and a crash on a float TTL. Each looked plausible from the code and took one script to disprove. That ratio is the argument for verifying findings before acting on them: a confident review is still a source of hypotheses, not conclusions, and three of the six specific claims I checked were wrong.
